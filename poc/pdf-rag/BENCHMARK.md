# embedder benchmark — pdf-rag POC

Run via `npm run benchmark` from `poc/pdf-rag/`. Compares four local ONNX embedders against `text-embedding-3-small` (OpenAI cloud) on the same English PDF corpus, with paraphrased queries generated by an LLM. The script auto-fetches the corpus and the bench-only ONNX weights with SHA256 verification on first run; subsequent runs are deterministic and free.

## V3 methodology

- **Corpus**: NIST SP 800-63B (Digital Identity Guidelines), public-domain US-government English-only technical PDF, ~80 pages → **480 chunks** after paragraph chunking (max 500 chars/chunk).
- **Queries**: **480 paraphrased questions**, one per chunk, generated by `gpt-5-nano` with validation (10–30 words; word-trigram overlap with source ≤ 0.5; not starting with "the passage says"-style prefixes). Cached in `bench-queries.json` keyed by corpus fingerprint.
- **Task**: for each query, the "correct" answer is the originating chunk. Metric is whether the embedder retrieves that chunk in the top-K.
- **Methodology fixes inherited from V2**: warm-up call before timing; RSS-based memory snapshots with explicit `global.gc()` (run with `NODE_OPTIONS=--expose-gc`); structured per-query JSON output at `BENCHMARK_RESULTS.json`; throughput micro-benchmarks at batch sizes 1, 10, 100.
- **V3-specific**: ingest is performed in batches of 32 to avoid the pathological case of padding all 480 variable-length chunks into a single 480×512 ONNX tensor. The throughput micro-bench still uses the requested batch sizes verbatim, so the numbers reflect what users get from naive (unsorted) batching.

Hardware: developer laptop (CPU inference for edge; cloud round-trip for OpenAI).

## What the numbers actually mean

### bge-base and bge-large beat OpenAI on retrieval quality

This is the single most consequential V3 finding. On clean English content with paraphrased queries:

- **bge-base** (110 MB): recall@1 **58.1%** vs OpenAI's 56.7% — a 1.4 pp lead.
- **bge-large** (336 MB): recall@1 **59.8%** vs OpenAI's 56.7% — a 3.1 pp lead.
- MRR follows the same pattern: 0.671 / 0.691 / 0.663.

These are not noise-level differences (n=480 gives ~±5 pp 95% CI); they're real and consistent across recall@1, recall@5, recall@10, and MRR. The bge-* family is contrastively trained on retrieval data, while text-embedding-3-small is a general-purpose encoder. **For retrieval, the specialized smaller models win on this corpus.**

### bge-small ≈ OpenAI quality at 1/30th the latency

bge-small (32 MB) hits recall@1 of 53.3% — only 3.4 pp behind OpenAI. At p50 12.3 ms vs OpenAI's 399.3 ms, **bge-small is 32× faster** at query time and runs entirely offline. For most chat-with-documents UIs this trade is overwhelmingly worth it.

### MiniLM is the latency floor

all-MiniLM-L6-v2 (23 MB) is the smallest and fastest (8 ms p50) but takes a noticeable quality hit vs bge-small (51.5% vs 53.3% recall@1). It's the right pick when 4 ms matters more than 2 pp of recall — i.e., very high-throughput query workloads.

### OpenAI wins decisively only on bulk ingestion

- **Ingest throughput**: OpenAI 37.7 chunks/s, bge-base 2.9 chunks/s, bge-large 0.76 chunks/s. For one-shot indexing of large corpora, OpenAI's API batching is hard to beat.
- **Throughput at batch=100**: OpenAI 11.2 ms/item, bge-large 2581 ms/item. The network round-trip is amortized over the batch; local CPU inference can't.

If your workload is "ingest 1M docs once, query forever," OpenAI's ingest speed buys you something real. If queries dominate, edge wins.

### Throughput-vs-batch shape differs by direction

| Embedder | batch=1 | batch=10 | batch=100 |
|---|---|---|---|
| bge-small | 16 ms/item | 80 ms/item | 249 ms/item |
| MiniLM | 8 ms/item | 40 ms/item | 62 ms/item |
| bge-base | 48 ms/item | 249 ms/item | 678 ms/item |
| bge-large | 245 ms/item | 804 ms/item | 2582 ms/item |
| OpenAI | 334 ms/item | 43 ms/item | 11 ms/item |

Edge models get **slower** per-item as batch size grows, because variable-length chunks force padding to the longest item and BERT self-attention scales O(seq²). OpenAI shows the opposite: batch=100 is 30× faster per item than batch=1, because the network round-trip dominates and is amortized.

**Practical takeaways:**
- For edge ingestion, sort and bucket inputs by length, or use small batches (8–32). The ingest-batched-by-32 approach in this benchmark recovers most of the throughput.
- For OpenAI, always batch as large as the API allows.

### Memory measurement caveat

The "model resident" RSS deltas in the per-model output are unreliable — `globalThis.gc()` only triggers V8's GC, not the C++-allocated ONNX tensor pools. The negative numbers (e.g., bge-large at "-5 GB") are GC noise. The actual memory cost of having a model loaded scales roughly with the FP32 weight count: ~50 MB for bge-small/MiniLM int8, ~150 MB for bge-base int8, ~400 MB for bge-large int8 plus several GB peak during inference for intermediate tensors. Take the BENCHMARK_RESULTS.json memory fields with that caveat.

## Scenario-based recommendation matrix

| If you need… | Pick |
|---|---|
| **Smallest install, fastest cold start** | `all-MiniLM-L6-v2` (23 MB) — 8 ms p50, 51.5% recall@1 |
| **Bundled-by-default option from `@trovec/embedder-edge`** | `bge-small-en-v1.5` (32 MB) — 12 ms p50, 53.3% recall@1, 32× faster than OpenAI |
| **Best quality / size trade-off** | `bge-base-en-v1.5` (110 MB) — 29 ms p50, 58.1% recall@1, **beats OpenAI on quality** |
| **Highest local quality, install size acceptable** | `bge-large-en-v1.5` (336 MB) — 93 ms p50, 59.8% recall@1, **best overall on this benchmark** |
| **Bulk-ingest huge corpora fast** | OpenAI `text-embedding-3-small` (37.7 chunks/s vs ~3 for bge-base) |
| **Multilingual content** | OpenAI (no English-only tokenizer on edge yet — out of scope for v0.2.0) |
| **No network, no per-call cost, fully offline** | Any edge model |

`@trovec/embedder-edge` ships only `bge-small-en-v1.5` in the npm tarball. To use bge-base, bge-large, or any other compatible BERT-WordPiece ONNX model, point `createEdgeEmbedder({ modelPath: <dir> })` at a directory containing the ONNX file and `tokenizer.json`. The package's low-level building blocks (`loadOnnxSession`, `runInference`, `Tokenizer`, `loadTokenizer`) are also exported for advanced composition (e.g., custom tokenizers for SentencePiece-based multilingual models).

## Caveats

- **Single corpus.** NIST SP 800-63B is one English technical PDF. Different domains (legal, medical, code, narrative) produce different numbers. The relative ordering between models is likely stable; absolute recall is corpus-dependent.
- **n = 480 queries** gives 95% CI of roughly ±5 pp. The 1–3 pp gaps between bge-base/bge-large/OpenAI sit at the edge of significance — the ranking is suggestive, not definitive. The bge-small-vs-OpenAI gap (~3 pp) is similarly modest.
- **gpt-5-nano-generated queries.** A different generator would produce different queries; an adversarial generator (queries deliberately phrased to fool embedders) would push recall lower for everyone.
- **INT8 quantization for all bge-* and MiniLM.** FP16 / FP32 variants would shift edge quality up by an estimated 0.5–1.5 pp at 2–4× the disk size. Not enough to change the recommendations, but worth knowing.
- **English only.** `bge-m3` and `multilingual-e5-base` are credible multilingual options but use SentencePiece tokenization, which `@trovec/embedder-edge` doesn't ship out of the box (a community SentencePiece tokenizer plugged through the new `tokenizer` option would unlock them).
- **CPU latency is laptop-class.** A faster CPU (e.g., AVX-512 server) would shrink the absolute latency numbers; the *relative* ordering would persist.

Re-run with `npm run benchmark`. `SKIP_OPENAI=1` runs only the local edge models. `BENCH_REGENERATE_QUERIES=1` regenerates the cached queries (requires `OPENAI_API_KEY` and one full pass of gpt-5-nano calls, ~15 min for this corpus).
